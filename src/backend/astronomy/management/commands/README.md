# ingest_space_weather の概要

1. 処理フロー（ステップバイステップ）
全体の流れは以下の4段階です。

現状把握（BigQueryへの問い合わせ）

まず BigQuery に「今、各メトリクス（X線、太陽風、Kp指数）はいつまでのデータを持っていますか？」と問い合わせます。

返り値例: {'xray_flux': 1月23日 10:00, 'solar_wind_speed': 1月23日 09:50, ...}

広範囲のデータ取得（Fetch）

NOAAから直近（デフォルト7日間）のデータをすべて取得します。

ここでは「重複などは気にせず、とりあえず確実な範囲」を取得します。

差分フィルタリング（Deduplication）

ここが今回実装した核となる部分です。

取得したデータをメモリ上（Pandas）で加工し、**「BigQueryの最新日時より未来のデータ」**だけを抽出します。

もし全てのデータが既に存在する場合（＝新しいデータがない場合）、ここで処理を終了します（早期リターン）。

データの保存（Ingest）

フィルタリングに残った「真に新しいデータ」だけを BigQuery に追加（WRITE_APPEND）します。

2. このコードのメリット
以前の「取得してそのまま全部Insertする」方式と比較して、以下の大きなメリットがあります。

① データの重複がゼロになる（データ品質の向上）
以前: 毎日実行すると、過去7日分のデータが何度も重複して保存されていました。分析時に DISTINCT する必要があり、非効率でした。

現在: 常にユニーク（一意）な時系列データが保たれます。グラフ化や分析が非常にスムーズになります。

② 何度実行しても安全（冪等性・堅牢性）
リトライに強い: もしネットワークエラーなどでジョブが失敗し、再実行したとしても、すでに保存されたデータはスキップされるため、データが壊れません。

スケジュールの柔軟性: 「1時間に1回実行」でも「1日1回実行」でも、コードを変更することなく、自動的にその間の差分だけを埋めてくれます。

③ 欠損（ギャップ）を防ぐ設計
取得範囲をあえて「7日間」と広く取っているため、万が一システムが3日間停止しても、復旧後の最初の実行で空白期間（3日分）を自動的に埋めることができます。

④ コストとパフォーマンスの最適化
不要なデータをInsertしないため、BigQueryのストレージ容量を節約できます。

また、Insert処理自体もデータ量が減るため、処理時間が短縮されます。

3. 技術的なポイント
Pandasの活用: 複雑な日付比較やフィルタリングを、SQLではなくPython側（Pandas）で処理することで、柔軟かつ高速にロジックを実装しています。

空データ対策（今回のBug fix）: フィルタリングの結果、データが0件になった場合に、空のDataFrameをBigQueryに投げようとしてエラーになるのを防ぐガード処理（if result_df.empty: return）が入っており、安定性が向上しています。
